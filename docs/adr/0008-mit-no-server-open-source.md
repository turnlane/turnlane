# ADR 0008: MIT ライセンスのオープンソースとして配布し、作者が運用するサーバーを持たない

- ステータス: Accepted（2026-10-02・2026-10-27 追記あり。末尾。Amended by [0015](./0015-extension-points-and-separately-licensed-additions.md): 拡張点と、公式の配布物に組み込む別ライセンスの拡張） / Amends [ADR 0002](./0002-local-sqlite-source-of-truth-hlc-lww-sync-later.md)、[ADR 0003](./0003-calendar-eventkit-phase0-google-api-phase1.md)
- 日付: 2026-10-02
- 関係: どちらも決定の一部だけを置き換える。ADR 0002 のうち「Phase1 以降に同期サーバ経由の同期を実装する」を取り消す（同期用カラムと `mutate()` / `change_log` は残す）。ADR 0003 のうち「Phase1 で Google Calendar API 直結を追加する」を取り消す（EventKit の決定は有効）

## Context

- dayline は AI セッションのメタデータ、自分のタスク、カレンダーの予定という、個人の作業の記録を扱う。利用者が「データが端末の外に出ていない」ことを、説明を信じるのではなくコードを読んで検証できる状態にしたい。
- 作者が運用するサーバーがあると、通信先・保存先・アクセス権限の説明と監査が必要になり、ソースを公開してもサーバー側の挙動は検証できない。サーバーの停止がアプリの停止になる。
- ADR 0002 は将来のマルチデバイス同期を自前の同期サーバで行う前提、ADR 0003 は Phase1 で Google Calendar API に直結する前提だった。Google API 直結には OAuth クライアントの登録と、公開時の sensitive scope の審査、トークンの保管と更新が要る。macOS では EventKit 経由で Google を含む全アカウントの予定を読み書きできる（ADR 0003）。
- 新しい AI エージェント（Cursor、Gemini CLI など）への対応は増え続ける。取り込みアダプタを利用者が自分で書いて持ち寄れる形にしたい。
- 実装はまだ始まっていない（Phase 0 の仕様段階）ので、方針を変えてもコードの手戻りは無い。

## Decision

1. **ライセンスは MIT** とする。リポジトリ全体（デーモン、CLI、Web UI、取り込みアダプタ、Swift ヘルパ）を同じライセンスで公開する。LICENSE ファイルは公開前に追加する（著作権者の表記は公開準備で確定する。phase0-plan の M6）。
2. **作者が運用するサーバーを持たない**。dayline の機能は利用者の端末の中だけで完結させる。
   - クラウド同期のサーバー、アカウント登録、ライセンスキーの確認、更新確認用の独自 API は作らない。
   - テレメトリ・クラッシュレポートの自動送信はしない（入れる場合は別 ADR で、明示的な opt-in を条件にする）。
   - ネットワークに出るのは、利用者自身が設定した外部コマンド・外部ツール経由の通信に限る（例: 利用者の `gh` CLI による GitHub の参照）。dayline のプロセスが作者の管理するホストへ接続するコードを持たない。
   - 配布物の取得（GitHub Releases、Homebrew）と、Tauri の自動更新を入れる場合の更新ファイルの取得は、GitHub Releases の静的ファイルを参照する。
3. **同期**（ADR 0002 を補正）: 同期用カラム（UUIDv7 の `id`、`hlc`、`device_id`、`deleted_at`、`sync_scope`）と `mutate()` / `change_log` は残す。ただし**同期サーバーは作らない**。複数端末の需要が出た場合は、利用者自身のストレージ（iCloud Drive などのフォルダ）を経由する方式を別 ADR で検討する。そのときも AI 取り込み系のデータは端末外に出さない。
4. **カレンダー**（ADR 0003 の一部を置き換え）: **Google Calendar API 直結はやらない**。カレンダーは macOS の EventKit のみとする。Web / モバイル版を作る予定も持たない。
5. **拡張はプラグインではなくリポジトリへの PR で受ける**。取り込みアダプタは `packages/collectors` の中で、他のパッケージに依存しない独立したパッケージとして切り出せる境界を保つ（phase0-plan 3.1）。外部サービスからのタスク取り込みは、ローカルの MCP / CLI（`add_task` の `source` と `external_id`）で受ける。dayline 側から外部サービスの API を呼びに行く連携は作らない。

## Consequences

- 「データは端末の外に出ない」を、ソースコードと通信先の不在で検証できる。プライバシーの説明が短く済む。
- 作者の運用コスト（サーバー費、障害対応、個人情報の管理、OAuth 審査）が発生しない。作者が開発をやめても、手元のアプリは動き続ける。
- マルチデバイス同期は当面提供しない。スマホからは EventKit で書き戻した時間ブロック（カレンダーの予定）だけが見える。
- Google 以外も含め、予定の鮮度は Mac のカレンダーアプリの同期間隔に依存する（ADR 0003 のとおり）。`calendar.provider` は `eventkit` のみとし、Google 用の列（`sync_token` など）は持たない。
- 同期用カラムと `change_log` は当面使われない列・テーブルになる。書き込み量が小さいことと、将来の方式（フォルダ経由など）に転用できることから残す。`change_log.pushed_at` は Phase0 では常に NULL。
- 新しいエージェントへの対応は、コミュニティからのアダプタ PR に頼れる。そのためにアダプタの公開 IF・フィクスチャの作り方・テストキットを文書化し、互換性を管理する必要がある。
- 公開にあたり、LICENSE、CONTRIBUTING、CODE_OF_CONDUCT、SECURITY、issue / PR テンプレート、サポート方針、git 履歴の個人情報監査、署名・公証と Homebrew での配布手順が要る（phase0-plan の M6）。
- 依存ライブラリのライセンスが MIT と両立することを確認する必要がある（GPL 系の依存を同梱しない）。

## 追記（2026-10-02）

Decision を補う PO の決定。上の Decision の本文は書き換えず、ここに記録する。

1. **LICENSE**: リポジトリ直下に MIT の `LICENSE` を追加した。著作権者の表記は個人名（2026-10-26 に Rootstack Inc. へ。追記の末尾）。Decision 1 の「LICENSE ファイルは公開前に追加する」は完了。
2. **更新確認は「サーバーなし」の例外として GitHub Releases に接続してよい**。Decision 2 の「dayline のプロセスが作者の管理するホストへ接続するコードを持たない」の例外として、dayline のプロセスが新しい版の確認のために GitHub Releases の静的ファイル（最新リリースに添付した `latest.json`）を取得することを認める。条件:
   - 接続先は GitHub Releases の静的ファイルだけ。作者が運用するホストや独自 API、`api.github.com` は使わない。
   - 送るのは HTTP リクエストだけで、Cookie、端末やユーザーの識別子、利用状況を付けない（User-Agent は `dayline/<version>`）。
   - 設定でオフにできる（既定はオン）。オフのときは接続しない。
   - README に接続先・送信内容・オフにする方法を書く。
   - 実装は phase0-plan の M6-12。Tauri の自動更新を入れる場合も同じ接続先と条件に従う。
3. **公開前の履歴監査で問題が見つかった場合**は、git 履歴を書き換えず、監査を通した状態から新しいリポジトリを作って公開する（書き換えの漏れのリスクより確実なため。phase0-plan の M6-7）。

### この追記の Consequences

- 「dayline のプロセスは外部に接続しない」は「更新確認を除いて接続しない。更新確認はオフにできる」になる。プライバシーの説明では、この1件を通信先の一覧に必ず載せる。
- 更新確認のオフ設定が守られていることを、偽の HTTP サーバを使ったテストで確認する必要がある。
- 監査で問題が出た場合、公開リポジトリには公開前の履歴が残らない。

## 追記 4（2026-10-27）: 同じ GitHub Releases からの取得と置き換え

4. **追記 2 の「確認だけ」を、同じ GitHub Releases から配布物を取得して置き換えることまで広げる**。デーモンは、更新確認で新しい版を見つけたら、`latest.json` の `url` の zip を取得し、検証してからアプリ（`install.json` の `appPath` の `Turnlane.app`）を置き換えてよい。条件:
   - 取得先は `latest.json` の `url` だけで、GitHub（`https://github.com/`）に限る。転送は GitHub のリリースの添付の置き場（`*.githubusercontent.com`）だけ追う。作者が運用するホストや独自 API は使わない。
   - 送るのは HTTP の GET だけで、Cookie、端末やユーザーの識別子、利用状況を付けない（User-Agent は更新確認と同じ `turnlane/<version>`）。
   - 入れる前の検証を必須にする: `latest.json` の sha256 との一致、`codesign --verify --deep --strict`、TeamIdentifier が動いている自分のバンドルと同じ（Team ID はコードに書かず自分のバンドルから読む）、`Info.plist` の版が `latest.json` の版と同じで今より新しい、`spctl --assess --type execute`（Apple の公証）が通ること。
   - 検証のどれか 1 つに落ちたら何も入れない（取得したものを消し、手動の案内に戻す）。置き換えは配置先の隣の一時名から rename で行い、途中で失敗したら前のものを戻す。配置先に書けなければ管理者権限を求めずに手動の案内に戻す。
   - 前の版のバンドル（`.Turnlane.app.old`）は置き換えと同じ実行では消さない（2026-10-29 の補正）。古い版のアプリ・デーモン・カレンダーヘルパはまだ終わる途中で、動いているプロセスの実行ファイルを消すと、まだ読み込んでいないページに触れたときに落ちる（0.7.1 → 0.7.2 の最初の自動更新で、Restart to update の間に古いアプリが「予期せず終了」した）。前の版のバンドルは、再起動の後に新しい版のデーモンが消す（新しい版のアプリがつながるか 60 秒が過ぎ、古い版のカレンダーヘルパが動いていないとき）。次の置き換えも最初に片付ける。
   - 設定でオフにできる（`update.download`、既定はオン。オフなら確認だけ。`update.check` をオフにすれば取得もしない）。
   - 新しい署名の鍵は持たない（検証は Apple の署名と公証で足りるため。Tauri の updater プラグインの鍵は使わない）。
   - 実装は `apps/daemon/src/update/`（`downloader.ts`・`verify.ts`・`install.ts`・`auto.ts`）。README に取得と置き換え、オフにする方法、`spctl` が Apple に接続しうることを書く。

### 追記 4 の Consequences

- 通信先の一覧は「GitHub Releases の `latest.json` と、新しい版の zip（どちらもオフにできる）」になる。
- `spctl` は、公証のチケットがバンドルに staple されていれば通常は接続しないが、チケットが無いと Apple に問い合わせうる。これは macOS の仕組みによる接続で、Turnlane の識別子は送らない。
- 取得・置き換えの経路が Homebrew の人と zip の人で同じになる。cask は `auto_updates true` にする（`brew upgrade` は `--greedy` のときだけ触る）。
- 置き換えの通しの確認は、実際のリリース（0.7.1 から 0.7.2）で初めてできる。
